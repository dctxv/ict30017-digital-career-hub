## 1. Explaining the prompt to the client

The client doubted that the reviewer uses Bangladeshi context at all. Rather
than argue, the pipeline was documented step by step with every rule quoted
verbatim from `ai-service/src/prompt/`.

The decisive evidence is a contradiction the system produces on purpose. Asked
about a photograph on a CV, the reviewer gives opposite answers depending on
where the application is going:

| Context | Instruction (verbatim) |
| ------- | ---------------------- |
| BCS / prescribed form | "a photograph, a signature, a declaration, parents' names ... are REQUIRED here. Never flag them, never recommend removing them, and never apply a score penalty for their presence." |
| Multinational | "The following are inappropriate for this employer and should each be raised as a SEPARATE formatting issue where present: ... Photograph" |

A generic resume tool has one rule for photographs and it is "remove it". That
rule fails every government applicant in Bangladesh.

Supporting figures, measured from `buildSystemPrompt()` rather than estimated:

```
Bdjobs, fresher, RMG      ->  15,634 chars   bdjobs_profile / unknown / fresher / rmg_manufacturing
BCS government form       ->  15,076 chars   government_form / government / unknown / unknown
Multinational, senior IT  ->  15,447 chars   unknown / multinational / senior / it_software
```

Four context dimensions — channel (8) x employer (8) x stage (6) x sector (8) —
compose **3,072 distinct rulebooks**, each around 3,900 tokens. Two blocks are
always on, four are selected per request, one is the output contract.

The explanation also states the limits plainly, because a document that only
sells reads as marketing: the reviewer cannot certify compliance with a
government circular, does not judge layout it cannot see, does not verify
truthfulness, and treats Bangladeshi convention as the *fourth* authority,
below the advertisement itself.

**Not committed** — this is a client-facing deliverable, not repository content.

## 3. Model comparison harness — `e060aa05`

**861 insertions.** `server/scripts/compare-models.js` (669 lines),
`docs/model_comparison.md` (176 lines), plus two exports and an npm script.

```
cd server
npm run compare-models -- --verify     # do the model ids resolve?
npm run compare-models                 # 18 runs, scored
```

### Why the existing harness could not be used

`ai-service/scripts/batch-review.js` ran the original nine-model P83 study, but
it sends this as the user message:

```
Please review the following resume:

<text>
```

Production sends `buildUserMessage()`, which also carries the application
context block and — on a Bangla run — the language reminder at the very end.
**That placement was the fix for the 26 August Bangla failure.** A Bangla
comparison run through the old harness would return 0% on every candidate, and
the models would take the blame for a harness bug. It is also hardcoded to
OpenRouter after the move to Google AI Studio.

`compare-models.js` imports the production builders, so if the prompt changes
the comparison changes with it. `buildUserMessage` and `normalizeResponse` were
exported from `resumeReviewer.js` for this reason.

### What it scores

Every check reuses the code that runs in the app — `resolveProtectedHeadings`,
`isMandatedFieldRemovalAdvice`, `checkBanglaOutput`, `ReviewResponseSchema`:

| Metric | Meaning | Target |
| ------ | ------- | ------ |
| Schema fail | Unusable response; the user sees "please try again" | 0 |
| Protected headings | Headings the server had to strip | low |
| **Mandated removals** | Advice that would get a BCS application rejected | **0** |
| Bangla coverage | Narrative fields actually written in Bangla | 100% |
| **Bangla violations** | Fields that must stay English but were translated | **0** |

Two need care. *Protected headings* never reach the user — the backstop strips
them — so a high count is not a broken review; it means the model is leaning on
the backstop rather than following the rule, which matters when the backstop
only covers the headings we thought to list. *Bangla violations* fail a run even
at 100% coverage: a violation means the tool is telling a candidate to paste
Bangla into an English CV. More Bangla, worse outcome.

### Three contexts, each catching a different failure

- `government_form` — the only context where mandated-field removal is
  measurable, and the failure with real consequences.
- `bdjobs_fresher` — protects the widest heading set, so over-flagging shows.
- `multinational_it` — protects nothing and *should* flag those same fields, so
  it catches a model that scores well by staying quiet rather than by knowing
  the rule.

### Verification status

The run path, scoring, aggregation and report were smoke-tested end to end
against a local stub speaking the OpenAI wire format (18 runs, PDF extraction
included), and the scorers were unit-checked against synthetic output with known
expected counts — 2 protected, 3 mandated, 1 Bangla violation, all matched.

**No real API call has been made.** Model ids are unverified; run `--verify`

## 4. Free-tier capacity, measured

Two ceilings, and they are nowhere near each other.

**Application cap** — `FREE_DAILY_REVIEW_LIMIT = 3` per calendar day
(`server/src/middleware/reviewQuota.js:22`). Premium and admin are uncapped.
Chatbot is separately capped at 10 messages/day.

**API cap** — measured against the live prompt:

| | Tokens |
| --- | ------ |
| System prompt (English) | 3,909 |
| System prompt (Bangla) | 4,159 |
| Resume text (the four test PDFs) | 374 – 623 |
| Output (real reviews in `docs/ai_model_testing/`) | ~600 – 1,800 |
| **Per review** | **~5,000 – 6,600** |

Against Flash free-tier limits of roughly 15 RPM / 1,500 RPD / 1M TPM, **RPD
binds first at about 1,500 reviews per day**. TPM never binds — 15 RPM at 6,000
tokens is ~90k of 1M. Those three figures come from third-party sources; Google
no longer publishes a fixed table, so the AI Studio project quota page is the
authority.

At 3 reviews/day per free account, ~500 users maxing out daily would be needed
to reach the API ceiling. The app cap is the real limit, not the provider.

Two caveats worth carrying forward:

- **The chatbot shares the key.** `ai-service/src/services/chatbot.js:141` uses
  the same `getGroqClient()` and `getModel(tier)`. Every chat message spends the
  same daily budget.
- **Free-tier prompts may be used by Google for training.** Resumes carry names,
  phone numbers and NID. PII redaction runs on the model's *output*, not its
  input, so the raw resume goes out as-is. This is the stronger argument for a
  paid tier than throughput is.

## 5. Blank page on any API failure — `479377a5`

A teammate cloned main and reported the backend would not run. The server was
running; the database was not reachable:

```
Server running on http://localhost:3000
[resources] list failed: password authentication failed for user "postgres"
```

His `server/.env` existed (the server exits at boot without the AI variables) but
`DB_PASSWORD` did not match his local Postgres role. That was his bug. The
*blank page* was ours.

### Root cause

`fetch()` does not reject on an HTTP error. A 500 resolves normally:

```js
const data = await response.json()   // { error: "..." }  <- an object
setResources(data)                   // no throw, catch never entered
```

Nothing failed until render reached `resources.filter(...)`, which threw
**outside** the try, escaped the effect and hit the error boundary. In the
console the real cause sat three errors above `resources.filter is not a
function`.

The tell that this was a bug rather than bad luck: the disciplines fetch on the
same pages survived, because it calls `data.map()` *inside* the try — so the
TypeError was caught and the fallback list rendered. Whether a failed request
blanked the page depended on where the array method happened to sit.

### Fix

`client/src/api/fetchList.js` checks `response.ok`, surfaces the server's own
error text, and returns an array or throws. Applied to Resources, Alumni and
CareerPaths, each of which now falls back to an empty list and shows a
translated "could not load" message. The password-authentication failure is
documented in the README, since "Server running" prints before every query
fails.
